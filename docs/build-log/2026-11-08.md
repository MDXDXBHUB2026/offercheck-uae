## Flaky test (FLK-1)
- **Found:** during the README task, one full `npm run check` failed. The test `src/lib/audit.test.ts` › privacy › "uses only fixed keys and fixed-vocabulary strings" timed out at the 5,000 ms default, and 778 of 779 tests passed.
- **What the test does:** it calls `runWithAudit` on 63 offers, one after another (2 fixtures, 43 dev cases and 18 holdout 1 cases). The longest of the 61 eval offers is 208 characters. Each call runs the rules and builds an audit chain, with one SHA-256 per entry through `crypto.subtle`. The test then checks every entry's keys and string values.
- **Measured** with the vitest JSON reporter. The test and the timeout were not changed.
  - `npx vitest run src/lib/audit.test.ts`, 10 runs: 111, 67, 59, 69, 56, 58, 56, 101, 77 and 89 ms. Each run passed 104 of 104 tests.
  - `npx vitest run`, 3 runs: 625, 442 and 523 ms. Each run passed 779 of 779 tests.
  - Stress check: 3 runs of `npx vitest run`, each started at the same time as `npm run build` in a second process. The test took 2,886, 643 and 1,450 ms. All 3 runs passed 779 of 779 tests, and vitest and the build both exited 0 each time. It did not time out.
- **Explanation:** not known. The work is small and took at most 625 ms in a full run, so the test's own work does not explain 5,000 ms. One possibility is that the worker was stalled by other load on the machine during that run, but this was not checked or reproduced. The stress check fits that idea: a parallel build made the test up to about 4.6 times slower than the slowest unloaded full run (2,886 ms against 625 ms). It still stayed under 5,000 ms, so the cause is not confirmed.
- **Still open:** FLK-1. It did not reproduce in these 16 runs, 3 of them under build load.

## QA fix batch: the QA fix batch commit (see git log)

From the owner's manual post-deploy QA. UI and docs only: `redFlag.ts` and `scoring.ts` unchanged. Score, bands, findings and weights unchanged.

- **UX-1, score chip.** The green "No risk indicators found" chip now shows only for score 0 with no finding and no warning. A low band with a finding or a warning only shows the amber chip "Low, review the findings below". Medium and high are unchanged. The screen-reader announcement uses the chip's wording. Replaces the earlier uncommitted UX-1 version ("Low score, N indicator(s) found", rule matches only); the amber `score-caution` CSS and its contrast test stay.
- **LANG-1, English-only notice.** A pure helper, `src/lib/textScript.ts`, counts letters by script. Tier 1, at least 50% non-Latin letters. Tier 2, under 50% but at least 10 non-Latin letters. The notice shows in the score card in every band, with fixed wording and no offer text. It is set from the submitted text at check time and cleared when a new check starts, never from the live text box. No new audit fields.
- **Nav "Soon" badge.** A `soon` flag on the four placeholder pages in `NAV_ITEMS`. The link's name is "<label>, coming soon". A test fails if a flag and its page disagree.
- **Approval wording.** After approval: "Reply approved and copied. Offer Check has not sent anything.", or "Reply approved. Offer Check has not sent anything." when the browser blocked copying. Before approval the wording is unchanged.

Decisions:
- **Tier 1 wording.** The request said "a score of 0 does not mean the offer is safe". The notice shows in every band, so it says "a low score or a score of 0 does not mean the offer is safe".
- **Tier 2 floor.** First 15, then 10 on the owner's call. A short Arabic fee demand such as `ادفع الرسوم` is 10 letters. A two-word name (7 letters) stays quiet. A three-word name such as `محمد بن راشد` (10 letters) gets the notice: an accepted trade-off. A design choice, not validated on real data.
