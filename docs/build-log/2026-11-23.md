# Build log: 2026-11-23

Production hardening Phase 4b, the light theme. Branch `theme-4b`, created from `origin/main` at `65c9e73` (the merge of PR #2, Phase 8 rules v2). Preview only: no merge, no deploy, no pull request.

## Built
- **Tokens.** Every colour in `src/app/globals.css` was already a custom property; a guard test (`src/app/themeTokens.test.ts`) now fails if a hex, rgb, hsl or named colour appears outside the token blocks. New roles for the primary action: `--action`, `--action-hover`, `--action-end`, `--action-end-hover` and `--on-action`. Their dark values are the old emerald, cyan and white, so the dark theme is unchanged (`--green-action*` and `--cyan-action*` stay defined, unused).
- **Dark did not move.** `src/app/darkTokens.snapshot.json` is the dark token block at `65c9e73`; the test fails if any value changes or an unlisted token is added. Separately, every `var(--…)` in the old and new stylesheet was resolved to its dark value and the rules compared: 485 rules, identical, except the removed `.chip-soon` rule (its only users were the two "coming soon" chips).
- **Light palette.** Warm off-white page (`#faf8f4`), white cards, dark slate text, one blue (`#1d4ed8`) for the primary action, links and the focus ring. Risk colours keep their meaning (high red, medium amber, low green) with the visible text labels unchanged. Glows and the aurora are quiet in light. Three identical copies of the light block: `:root[data-theme="light"]`, `:root[data-theme="system"]` inside `@media (prefers-color-scheme: light)`, and the print block (paper is always light, whatever the theme on screen).
- **Contrast, tested.** `src/app/themeContrast.test.ts` checks 60 pairs per theme from the tokens (55 colour pairs, text 4.5:1 and graphics 3:1, plus 5 hero text colours over the worst video pixel) and writes the table `docs/theme-contrast.md`. One real failure was fixed in the palette, not by lowering the bar: light hero text in green over a black video pixel was 4.39:1, so the light glass went from 0.90 to 0.92.
- **Mechanism.** `src/components/shell/theme.ts` (store, same pattern as the language, animation and text size stores), key `offercheck_theme_v1`, values `system`, `dark`, `light`; no saved value means the dark default. A script in the head (`THEME_INIT_SCRIPT`, `src/lib/themeInit.ts`) sets `data-theme` on `<html>` before first paint; `restoreTheme()` does the same on mount (it also covers React's development remount clearing the attribute, as the Next.js guide `preventing-flash-before-hydration.md` describes). The script carries this request's CSP nonce, read from the request's own `Content-Security-Policy` header (`nonceFromCsp`); `src/lib/csp.ts`, `src/proxy.ts` and the security headers are untouched and `'unsafe-inline'` is still absent from script-src. The browser's `theme-color` meta tags use the media-query form, and an explicit Light or Dark choice also sets them.
- **Settings.** The Theme row has System, Dark and Light working; the "coming soon" chips, the `THEME_NOTE` sentence and their Arabic entries were removed. No new user-facing string: "Theme", "System", "Dark" and "Light" already had Arabic.
- **Clear my data** also removes `offercheck_theme_v1` and returns the page to dark.

## Cause of the Arabic "cut" flags from the Phase 4b sweep
Not clipped text. The sweep flags an element with `overflow: hidden` whose `scrollWidth` is more than its `clientWidth`. The header tabs have `overflow: hidden` for the hover-sheen decoration: a `::after` gradient parked at `translate: -100% 0` (and moved to `100%` on hover). In right-to-left text the space to the left is scrollable overflow, so a 105px tab reports `scrollWidth` 209 (twice its width); in English the same decoration sits in the unreachable direction and reports nothing. Measured in Chrome at 360px: the text of every tab lies inside its box in both languages. Nothing was fixed because nothing is clipped; the same flags appear again in the final sweep (48 of the 96 page runs, Arabic only, none in English).
